Libro Spec: GUI + Headless Server Remote Architecture

Proposal for making Libro GUI connect to one or more headless Libro runtimes, either locally or through SSH to remote machines. This is not the current CLI/runtime behavior.

Status: proposal / design note, updated after native PTY migration
Current implementation: libro starts one local HTTP/WebSocket server on port 8100 and opens the Electron desktop shell by default. libro --no-desktop exists today but should be removed by this refactor. libro --version prints the version.
Current terminal baseline: terminals no longer use ttyd; Libro serves xterm.js panels over /terminal/ws/<id> backed by Go PTYs.
Proposed architecture: every project belongs to a runtime machine; each runtime machine has one reusable headless Libro daemon; the GUI becomes the desktop shell, connection manager, and local-services owner.
Proposed security rule: passwords/vault stay on the GUI machine, never on the remote headless server by default.

1. Target Model

Local machine
  Libro GUI / Electron

    - SSH tunnel manager
    - browser/webview shell
        |

Runtime machine A / B / local

In the proposed architecture, the same GUI connects to the same headless API for both local and remote projects. The only difference is how the GUI reaches each runtime. Because terminals are now native PTY WebSockets, remote servers do not need ttyd or per-terminal TCP ports.

The GUI can manage multiple runtime machines at once. Projects are grouped by runtime machine in the project picker, and command execution is routed by the active project's runtime.

Current local runtime
libro starts the local server and desktop shell together. The current --no-desktop flag is removed by the remote refactor instead of kept as an alias.
Proposed local runtime
GUI starts or connects to one local libro headless daemon and asks it to open local project paths.
Proposed remote runtime
GUI uploads/starts one libro headless daemon per remote user/machine through system SSH and connects through a local port forward.
Password vault
Currently stored in the local Libro database. In the proposal, it stays owned by the GUI process and stored on the local desktop machine.

2. Current Code Baseline

The remote architecture should build on the current post-ttyd implementation:

AreaCurrent state
Terminal backendinternal/components/terminal.go owns TerminalManager, PTY startup, resize/input handling, and /terminal/ws/<id>.
Terminal UITerminal apps render normal DOM containers with bundled xterm.js and fit addon assets from assets/xterm/. No iframe is used for terminal apps.
State modelApplication uses TerminalID and TerminalReady instead of a ttyd URL/port.
Session authorizationThe terminal WebSocket validates that the requested terminal belongs to the active Libro session. Full connection-token auth is still part of the headless work.
Removed dependencyNo ttyd process, proxy route, or per-terminal TCP port allocation remains.

3. Why This Architecture

  • Local and remote projects use one consistent runtime model.
  • Headless Libro sees its filesystem as local, so existing os.Stat, git, nvim, and command logic stays simple.
  • Remote support avoids adding if remote { ssh ... } inside every feature.
  • It matches the successful architecture used by VS Code Server, Cursor, and Zed remote server.
  • The GUI can reconnect to already-running headless servers.

4. CLI Shape

Current commands before this refactor:

libro                 # start local server and desktop GUI
libro --no-desktop    # start local server only, on port 8100; remove in this refactor
libro --version       # print version

Proposed future commands:

libro                         # default desktop GUI
libro gui                     # explicit desktop GUI
libro headless                # HTTP/WebSocket runtime daemon only
libro /home/me/code/app       # open local project path
libro ssh://my-server/path    # open remote project path through SSH
libro --version               # print version

--no-desktop is not kept as a compatibility alias. Use libro headless for runtime-only mode.

Proposed headless command

libro headless \
  --host 127.0.0.1 \
  --port 0 \
  --token <random-token> \
  --json-ready

Headless starts a runtime-machine daemon. Workspaces are opened later through the API, not by starting one process per workspace. Headless prints exactly one machine-readable ready line to stdout. Logs go to stderr.

LIBRO_READY {"host":"127.0.0.1","port":39123,"pid":12345,"version":"0.1.0"}

5. Proposed Local Project Flow

User command:

libro ~/code/app

GUI would perform:

  1. Start or connect to the local headless daemon bound to 127.0.0.1.
  2. Read LIBRO_READY if a new daemon was started.
  3. Register the local runtime in the GUI connection registry.
  4. Ask the local daemon to open or switch to ~/code/app.
  5. Render the project in the Electron GUI.
libro headless --host 127.0.0.1 --port 0 --token xxx --json-ready

GUI connects:
http://127.0.0.1:39123/?token=xxx

GUI API call:
open workspace /home/me/code/app

6. Proposed Remote Project Flow

User target:

ssh://my-server/home/me/code/app

GUI would perform:

  1. Resolve SSH target using the SSH alias exactly as typed and the user's ~/.ssh/config.
  2. Open/reuse system SSH ControlMaster connection if supported.
  3. Probe remote OS/arch with uname -s and uname -m.
  4. Ensure a remote Libro binary exists under ~/.libro/server/<version>/libro, installing automatically after user confirmation if missing.
  5. Read remote daemon metadata from ~/.libro/server/runtime.json if present.
  6. Attach blindly to an existing daemon if it appears reachable.
  7. If no daemon is reachable, start remote libro headless bound to remote 127.0.0.1.
  8. Read LIBRO_READY from SSH stdout and write/update runtime.json with file mode 0600.
  9. Open or reuse an SSH tunnel from a local port to the remote headless daemon.
  10. Ask the remote daemon to open or switch to /home/me/code/app.
  11. Render the remote project inside the existing Electron GUI.
# remote startup
ssh my-server '~/.libro/server/0.1.0/libro headless \
  --host 127.0.0.1 \
  --port 0 \
  --token xxx \
  --json-ready'

# tunnel
ssh -N -L 127.0.0.1:17645:127.0.0.1:39123 my-server

# GUI opens
http://127.0.0.1:17645/?token=xxx

# GUI API call
open workspace /home/me/code/app

7. Proposed Remote Binary Installation

Install path:

~/.libro/server/<version>/libro

During connection, the GUI probes the remote machine and automatically installs the remote binary after user confirmation when the needed binary is missing. If an existing daemon is already running, GUI attaches blindly first and only warns if an API compatibility check fails. GUI must support two installation paths:

ModeBehavior
Upload from localGUI ships or downloads the correct binary, then uploads via scp/sftp.
Download on remoteRemote uses curl or wget to fetch the release binary.

Upload fallback is important for servers without internet access. Installation uses the system ssh plus scp/sftp binaries so existing SSH config, keys, agents, jump hosts, and ControlMaster behavior are reused.

8. Proposed Authentication and Security

  • Headless binds to 127.0.0.1 by default.
  • Headless uses a random daemon token for v1.
  • The token is passed in the initial URL/query param and required on all HTTP, WebSocket, terminal, asset, and API endpoints.
  • Reusable remote daemon metadata, including the token, is stored in ~/.libro/server/runtime.json with file mode 0600.
  • Terminal WebSocket access must check both the connection token and terminal ownership.
  • Remote headless should never listen on 0.0.0.0 unless user explicitly opts in.
  • SSH is responsible for transport security in remote mode.
  • Logs must not print tokens.
  • Cookie/header-based auth can replace the query-token bootstrap later, but is not required for v1.

9. Proposed Password Vault Rule

In remote mode, passwords must be stored where the GUI runs, not where headless runs.

Therefore:

  • The encrypted password DB stays on the local GUI machine.
  • Remote headless does not create/read/write password vault entries.
  • Remote headless never receives password metadata, encrypted blobs, entry names, URLs, usernames, or decrypted secrets.
  • Password command palette UI is implemented by the GUI shell or a local-only service, not by remote headless.
  • Copy username/password writes to the local clipboard.
  • If a remote terminal needs a secret, user pastes it intentionally into the terminal.

Implementation options

OptionDescriptionRecommendation
GUI-local overlayPassword dialog is rendered by local GUI on top of remote web UI.Best long-term security boundary.
Local password APIRemote page sends a message to Electron preload/main process to open local password UI.Good practical implementation.
Remote vaultPassword DB stored on remote headless server.Do not use by default.

11. Runtime Connections and Routing

  • The GUI maintains a connection registry for local and remote runtime machines.
  • A runtime identity uses the SSH alias exactly as typed for v1; no canonical host normalization is required initially.
  • The project picker groups projects by runtime machine.
  • There is only one GUI-level home project, not one home project per runtime machine.
  • Each project stores or resolves a runtime_id and path.
  • Terminals, nvim, git, worktree, run, debug, and agent commands execute on the active project's runtime machine.
  • One GUI instance can connect to multiple runtime machines at once.
  • One headless daemon serves one GUI client at a time in v1. Concurrent GUI clients are not supported; the daemon should report busy rather than merging sessions.
  • If GUI and daemon versions differ, GUI still attaches first. It warns only if the API compatibility check fails.
  • Remote daemons start on demand only. No systemd, launchd, or persistent service installation is required for v1.

12. Proposed Headless API Responsibilities

Headless would own:

  • Project/workspace filesystem access.
  • Project creation for its own machine.
  • Git and worktree operations.
  • Native PTY terminal sessions over /terminal/ws/<id>.
  • Running nvim, agent CLIs, test commands, debug commands.
  • Workspace-specific saved apps.

Minimum API surface

Exact route names can follow the existing g-sui action style, but headless must expose these capabilities behind token auth:

CapabilityPurpose
runtime infoReturn daemon PID, version, API version, runtime ID, and active GUI-client status.
open workspaceAdd or switch to a project path on this runtime machine.
list projectsReturn projects/worktrees owned by this runtime for grouped project picker rendering.
start terminalCreate PTY-backed terminal sessions for a project path.
terminal WebSocketAttach xterm clients to /terminal/ws/<id> with token and ownership checks.
run commandRun saved commands, nvim/vim, agent CLIs, and debug/test commands on the runtime machine.
git/worktreeExpose git status and worktree create/switch operations for runtime-owned projects.
doctorReport shell, PTY, git, editor, runtime, and agent availability.

Headless would not own:

  • Local desktop window lifecycle.
  • Local encrypted password vault.
  • SSH connection configuration.
  • Local OS clipboard secrets, except ordinary page copy operations.

13. Proposed GUI Responsibilities

  • Start local headless servers.
  • Install/start remote headless servers through SSH.
  • Maintain SSH tunnels and reconnect logic.
  • Maintain the runtime connection registry.
  • Render Electron window/webviews.
  • Own password vault and secret copy UX.
  • Manage remote connection profiles.
  • Forward ports for remote dev servers.
  • Store browser downloads on the GUI machine.

14. Proposed Port Forwarding for Remote Dev Servers

If remote terminal starts:

npm run dev
# remote app listens on 127.0.0.1:3000

When the user opens localhost:3000 or 127.0.0.1:3000 inside a remote project, GUI treats it as remote localhost, creates or reuses a tunnel, and opens a local forwarded URL:

ssh -N -L 127.0.0.1:3000:127.0.0.1:3000 my-server

If the requested local port is already occupied, GUI chooses a free local port and rewrites the browser panel URL:

ssh -N -L 127.0.0.1:17645:127.0.0.1:3000 my-server

browser opens:
http://127.0.0.1:17645

External URLs like https://github.com remain purely local Electron webviews. Only loopback URLs are interpreted as remote-runtime URLs. Command palette fallback actions:

  • remote forward port
  • remote open localhost port
  • remote stop forwarded port
  • remote list forwarded ports

15. Remote Doctor

After connecting, GUI/headless should expose a doctor report:

libro doctor --json

Checks:

  • shell availability
  • PTY support via github.com/creack/pty
  • git optional
  • nvim/vim optional
  • common runtimes: node, npm, pnpm, go, python, cargo, docker
  • agent CLIs configured by user

Missing project tools should be shown as install hints, not as connection failures.

18. Migration Plan

  1. Introduce libro headless mode using the current Go server without Electron.
  2. Add token auth and LIBRO_READY startup protocol.
  3. Change GUI startup to always connect to a headless URL, even for local projects.
  4. Move password vault into GUI-local service and remove remote server dependency for secrets.
  5. Native Go PTY terminals are already implemented locally; harden them under headless token auth.
  6. Add local headless daemon launcher.
  7. Add remote SSH installer, daemon manager, tunnel manager, and runtime.json reconnect metadata.
  8. Add remote project URL parsing: ssh://host/path and optionally host:/path.
  9. Add GUI connection registry and project grouping by runtime machine.
  10. Add lazy remote localhost forwarding plus manual forwarding commands.
  11. Add reconnect/reuse of existing runtime-machine daemons.

19. Proposed Acceptance Criteria

  • Opening a local folder starts or reuses the local headless daemon and opens that path as a project.
  • Opening ssh://host/path installs/starts or reuses one remote headless daemon for that SSH alias and connects through SSH tunnel.
  • One GUI can manage local plus multiple remote runtime machines in one window.
  • Project picker groups projects by machine and does not create one home project per remote runtime.
  • Terminal, nvim, git, worktree, run, debug, and agent commands execute on the headless runtime machine through native PTYs.
  • Remote terminal support does not require ttyd or per-terminal TCP ports.
  • Password vault remains on the GUI machine and is not created on the remote server.
  • Remote headless never receives password metadata or encrypted password blobs.
  • Remote headless binds to remote localhost only and requires token auth.
  • Remote localhost web apps can be opened through lazy managed SSH port forwarding from local Electron browser panels.
  • Browser downloads are saved on the GUI machine.
  • Missing remote tools produce clear doctor/install-hint messages.
